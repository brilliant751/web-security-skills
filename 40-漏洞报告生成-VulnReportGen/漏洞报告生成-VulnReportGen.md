# 漏洞报告生成 (Vulnerability Report Generation)

## 概述

漏洞挖出来、复现成功，事情只做了一半。剩下那一半是把过程写清楚交出去——**审核员不会重挖一遍漏洞，他只会按你写的步骤走一遍**。报告写得让人复现不出来，漏洞是真的，结果也是退单。

退单原因主要有五类：

| 退单类型 | 典型表现 | 根因 |
|:---|:---|:---|
| 复现不了 | 步骤缺前置条件、少了某个账号或参数、跳步 | 按「我知道漏洞长什么样」的视角写，不是按「别人什么都不知道」的视角 |
| 危害不足 | 只证明「有个漏洞」，没证明「能造成什么后果」 | 危害说明写成了形容词，没有可核对的数据与范围 |
| 证据缺失 | 没有请求包、没有关键截图、只有一张结果图 | 测试时没留证，整理时又靠回忆补 |
| 重复或拆分 | 与已公开漏洞重复；同一个源的问题拆成几份交 | 动手前没查这个点有没有人报过、判不出哪些属于同一个漏洞 |
| 越界取证 | 复现步骤里出现了超出授权的动作或抓取的数据 | 不清楚这类漏洞「验到什么程度就该停」 |

前三种是白干一场；后两种更重——**两家平台都把这类行为写进了处罚条款**，轻则忽略该漏洞，重则限制提交权限。

还有一类是这两年变多的：**报告是 AI 生成的，但没有人工复现过**。这一点两家都专门发了公告：

- 漏洞盒子《关于规范 AI 辅助漏洞报告提交标准的公告》——AI 可以用于辅助挖掘、POC 编写和报告整理，但**报告提交前必须完成人工验证**，且要提供影响说明、复现步骤、可验证的 POC 或关键请求包、关键步骤与结果截图、触发条件与影响范围。
- 补天《关于提交 AI 生成漏洞报告的行为规范及违规处置通告》——**使用 AI 辅助生成内容，须逐条人工验证与核实**；禁止把 AI 生成的、未经人工验证的报告批量提交；报告须包含漏洞 URL、漏洞所在功能点、漏洞验证过程、完整数据包及 POC、漏洞验证证明、危害证明，并配上细节截图与文字描述。

两家的处置节奏也一致：累计超过 3 个无效报告会被提醒，超过 5 个扣信誉值 / 限制提交权限，情节严重者封号。

这条技能就是按上面这些要求展开的：**AI 负责把已确认的事实组织成平台要的结构，人负责验证、补证据，也负责判断这一步该不该做。**

## 核心技能

### 1. 报告九段结构（按此顺序写）

| 序号 | 段落 | 写什么 | 最常见的退单点 |
|:---|:---|:---|:---|
| 1 | 漏洞标题 | 资产标识 + 漏洞类型，一句话 | 用了「疑似 / 可能 / 存在风险」；只写「SQL 漏洞」这种不点位置的标题 |
| 2 | 影响资产 | 漏洞地址（**文字 URL**）、受影响的功能点与组件、归属说明 | 只给截图不给文字 URL；不说明资产归属 |
| 3 | 漏洞类型 | 按平台预置分类选 | 选错或不选 → 直接忽略处理 |
| 4 | 危害等级 | 按第 5 节的判据给 | 自评偏高或偏低，且没写判定依据 |
| 5 | 漏洞描述 | 组件与版本、漏洞编号、触发条件、影响面，只写已确认的事实 | 混进未验证的推测；出现目标上不存在的接口或参数 |
| 6 | 复现步骤 | 编号呈现，从零讲起（前置条件、账号、工具），每步配截图 | 步骤不完整，审核员按步骤走复现不出来 |
| 7 | 请求与响应 | 原始报文**照录**，不改写、不补全；POC 给可复制的文本 | 用截图代替文本；把请求「整理」过导致失真 |
| 8 | 危害说明 | 能直接做到什么操作、影响到什么范围 | 写「危害严重」这类形容词，没有数据与边界 |
| 9 | 修复建议 | 具体到版本号、配置项或代码行；给思路或伪代码 | 只写「升级补丁」「加强过滤」→ 无效修复建议会被忽略 |

九段都要有，缺哪段都会有对应的退单理由。顺序不要调——审核是按这个顺序看的。

### 2. 逐段写法

**① 漏洞标题**

格式：`[资产标识] + [漏洞类型]`。资产标识带上域名或系统名，漏洞类型点到具体位置。

```
✅ shop.example.com 订单详情接口存在水平越权漏洞，可查看任意用户订单
✅ 某企业官网 showforum.asp 请求存在 SQL 注入漏洞
❌ 某网站存在漏洞
❌ SQL 漏洞
❌ 疑似存在 SQL 注入，可能影响数据库
```

「疑似 / 可能 / 存在风险 / 严重」这类词一律不写，也**不要只写个漏洞类型**——漏洞盒子的公益 SRC 提交页写得很明确：直接填「SQL 漏洞」「存在问题」这类标题的报告一律忽略。标题只陈述**确定发生过的事**：漏洞已经被你验证过了，不需要留余地。

**② 影响资产**

文字地址优先，写成完整 URL（含域名、路径与出问题的参数），能直接复制粘贴打开：

```
漏洞地址：http://shop.example.com/api/order/detail?orderId=10087
影响功能点：订单详情查询接口
涉及组件：ThinkPHP 5.0.20
资产归属：该域名 ICP 备案主体为「XX 科技有限公司」
```

三处容易漏：**URL 要文字不要截图**（漏洞盒子明确要求文字 URL，补天的模板里还有一项单独的「首页截图，含地址栏」）；**URL 要写全**，只丢一个 IP 或裸域名，很多项目不收；**归属要说清**——补天提交模板中专设「归属证明」一项（用公开信息证明该资产确实属于该厂商），漏洞盒子的厂商信息填错或不填会被直接忽略。归属不明或不匹配，漏洞本身再真也可能进不了审核。

**③ 漏洞类型 / ④ 危害等级**

都从平台预置的分类里选，不自己造词。类型选错或不选会被直接忽略，等级按第 5 节判据给，拿不准选中危，让平台定夺。

**⑤ 漏洞描述**

四要素：**组件与版本 → 漏洞编号 → 触发条件 → 影响面**。只写验证过程中真实出现的东西。

```
目标使用 ThinkPHP 5.0.20，该版本受 CVE-2018-20062 影响。
未授权状态下访问 /index.php?s=/index/\think\app/invokefunction 路由，
function 参数可控，可调用任意 PHP 函数。经测试，system 函数可执行，
影响范围为该站点 Web 服务权限下的整台服务器。
```

边界很清楚：**没验证过的一句不写**。写了「可读取全部用户数据」但只读到一条，审核员复测对不上，整份报告的可信度就没了。

**⑥ 复现步骤**

按「别人什么都不知道」的视角写，编号呈现，每步只做一件事，配一张截图。**写到第 3 节那张表的「停」为止**。

```
1. 环境准备：浏览器 + 抓包工具（Burp Suite），无需登录
2. 访问 http://shop.example.com/index.php?s=/index/NotExistClass/foo
   页面报错信息中可见框架版本为 5.0.20
   【截图 1】访问报错页，页面中可见 V5.0.20
3. 构造并发送如下请求
   GET /index.php?s=/index/\think\app/invokefunction&function=call_user_func_array&vars[0]=system&vars[1][]=id HTTP/1.1
   Host: shop.example.com
   【截图 2】发送请求，请求包中 function 参数可见
4. 响应体首行返回 uid=33(www-data)，说明命令执行成功
   【截图 3】响应回显中可见 uid=33(www-data)
```

三个硬要求：**从零开始**（不假设读者知道你在说什么）、**每步一图**、**不跳步**（顺手做的事也写出来）。漏洞盒子对这一段的要求是「复现过程完整，**无需二次沟通或补充数据**」——审核要能照着一遍跑通。

**⑦ 请求与响应**

原始报文照录，用代码块贴文本，不要截图。抓包工具里直接导出，一个字符都不要改——包括看起来多余的头。POC 也一样，**给可复制的文本字符串，不要只放图片**（部分厂商项目明确写了这一点；编辑器把代码转义了，就用附件补）。

```
GET /api/order/detail?orderId=10087 HTTP/1.1
Host: shop.example.com
Cookie: PHPSESSID=aaaa1111bbbb2222
User-Agent: Mozilla/5.0 ...
```

```
HTTP/1.1 200 OK
Content-Type: application/json

{"orderId":10087,"receiver":"张三","phone":"138****8000","address":"..."}
```

响应只贴**能证明结论的那几行**，不要整页 HTML 堆上去。涉及他人隐私数据时打码，但打码不能把证明力打没——要让人看出「这确实不是当前账号的数据」。

**⑧ 危害说明**

从「能做什么」写到「影响多大」，落到可核对的量上：

```
可未授权执行任意系统命令，权限为 Web 服务账号（www-data），
可读取站点配置文件与数据库连接信息，进而横向获取数据库内的业务数据。
```

平台看这一段判断等级：涉及多少用户数据、是否触及资金、是否需要登录，都在这几句里体现。**注意口径**——说自己「证明可读取数据库敏感表」就够了，不要顺着写成「已获取全部用户数据」，那既夸大了影响，也等于自曝越界。

**⑨ 修复建议**

具体到版本、配置项或代码行，最好给思路或伪代码。漏洞盒子明确要求「对开发有较大实用性」——**无效的修复建议会被忽略处理**：

```
✅ 将 ThinkPHP 升级至 5.0.24 或以上（5.0.23 仅修复 CVE-2018-20062，仍受 CVE-2019-9082 影响）；
   若暂时无法升级，在入口处过滤路由参数中的反斜杠与 think\ 关键字，并对 invokefunction 做白名单限制。
❌ 建议修复该漏洞，及时更新补丁。
```

### 3. 验到什么程度就算够（按漏洞类型）

报告里的复现步骤能不能这么写，先看验证时有没有越过边界。两家平台的规范把每个类型的「证明上限」写得很具体——补天的《专属 SRC 测试行为规范》逐类型点了名，漏洞盒子的《平台通用评定原则》补了判定口径。写报告时按这张表裁剪步骤。

| 漏洞类型 | 证明到这一步就停 | 明确禁止 |
|:---|:---|:---|
| 命令执行 / getshell | 执行一条只读命令（whoami、id）看到回显即停 | 读取源码、配置文件、敏感数据；内网横向、提权、植入后门；建立反弹连接 |
| 文件读取 | 读一个通用证明文件（/etc/passwd、web.xml、index.php 之类非核心业务文件） | 打包下载整个应用源代码 |
| SQL 注入 | 用报错或延时证明注入存在；**注出其中一条数据**证明危害 | 拖动整库整表（拖库）；`into outfile` 写文件；批量拉取业务敏感表 |
| SSRF | 证明能访问内网或探测到一个端口、拿到 Banner | **只拿 DNSLog 当唯一证明**（要么能说明请求可构造）；大范围端口扫描；把漏洞当跳板打内网其他主机 |
| 越权 | 用自己可控的两个账号交叉验证，看到他人数据一条即停 | 无差别、大范围遍历接口和用户 ID；增、删、改 |
| XSS | 一段能弹窗或能证明 JS 上下文执行的 payload + 截图 | 用 XSS 平台做 Cookie 劫持、挂马、钓鱼；在页面里插入影响正常访问的冗余数据 |
| 弱口令 / 爆破 | 前台撞库要有成功案例；后台只收「确实登进去了」的案例 | 仅能爆破、没进后台就提交（会被忽略） |
| 已获取系统权限后 | 证明「我拿到了」即停 | 下载源代码审计（须先联系审核员、经厂商同意后才能继续） |

用法很直接：**报告里的复现步骤只写到「停」那一步**。多写一步，等于自己交代了一次越界。反过来，如果实际验证时已经走过了头，报告里也不要写——补天把「拿权限后读源码、横向、植入后门」直接写成了红线，不是建议。

> 依据：补天《重申专属 SRC 测试行为规范及违规处理标准》（2026-03）与漏洞盒子《平台通用评定原则》。各厂商项目另有附加要求——有的项目不收反射型 XSS、DOM XSS、客户端拒绝服务漏洞，有的要求提供测试账号。**动手前先看项目页的测试范围。**

### 4. 证据怎么留（截图 / 请求包 / 视频）

| 证据 | 要求 | 谁来做 |
|:---|:---|:---|
| 关键步骤截图 | 每步一张；浏览器地址栏、请求参数或返回特征要可见 | 人工（验证时顺手截） |
| 首页截图 | 含地址栏，补天模板里是独立一项 | 人工 |
| 原始请求与响应 | 从抓包工具导出文本，不改动 | 人工 |
| POC | 可复制的文本，不只给截图 | 人工 |
| 复现视频 | 可选；补天支持上传 MP4（表单标注约 50MB 以内，超了先压缩） | 人工 |
| 危害证明数据 | 点到为止：能证明存在即可，不批量拉取用户数据 | 人工 |

**截图缺口的处理约定**（AI 整理阶段看不到你的截图，必须留位）：

在需要插入截图的位置单独写一行标注，格式统一为：

```
【截图 N】这一步要拍什么，例如：访问报错页，页面中可见 V5.0.20
```

整理完成后，把全部标注汇总成一份「待补截图清单」一起交给人工，**不要默认截图已经有了**。审核员看不到截图就等于证据缺失，这一条是 AI 整理报告时最容易埋的坑——两家平台都点了名：无利用截图、无详细过程的报告会被忽略。

### 5. 危害等级怎么定

| 等级 | 判据 | 例子 |
|:---|:---|:---|
| 严重 | 直接获取服务器权限、核心数据库或资金操作能力 | 未授权 RCE、可任意转账 |
| 高危 | 可批量获取用户敏感数据、越权操作他人账号、可向服务器写入内容 | 可遍历他人订单（含手机号地址）、任意文件上传 |
| 中危 | 需特定条件才能利用、影响限于当前用户、需要受害者交互 | 存储型 XSS、单账号内的越权 |
| 低危 | 信息泄露类，无直接业务影响 | 目录列表、版本号泄露、无敏感信息的报错 |

**有一条硬尺子要知道**——漏洞盒子对「严重敏感身份信息」给了定义：一条记录**至少命中 3 个敏感字段**（姓名 / 身份证、银行卡信息、手机号 / 邮箱、密码、地址）才算数，只涉及一两个字段的会按敏感程度降级。所以危害说明里**把命中的字段数出来**：「可获取姓名、手机号、收货地址（3 个敏感字段）」比「可获取大量用户信息」有力得多，也直接决定等级。

三条实操建议：

1. **等级要配得上描述**。写「高危」就要在危害说明里给出对应的数据量或权限范围，否则审核员会降级。
2. **拿不准就填中危**。平台会按自己的标准复核，自评偏高比偏低更容易引起争议。
3. **补天偏业务影响**——是否涉及资金、是否涉及用户敏感数据、涉及多少量，权重比技术难度高。同是越权，能看手机号和只能看昵称，等级差一档。

另外两条会影响等级的客观因素，写之前先想清楚：**边缘 / 废弃业务系统上的漏洞，两家都会酌情降级**；**同一系统短时间内被报出大量同类型高危漏洞时，平台会与厂商沟通，通常只审前三个，其余降级处理**——这也是为什么要挑有价值的点报，而不是把一个系统上的同类问题全搬上去。

### 6. 平台差异（补天 / 漏洞盒子）

两家的字段大同小异，差别主要在提交结构、审核侧重和忽略触发条件：

| 维度 | 补天 | 漏洞盒子 |
|:---|:---|:---|
| 提交结构 | 公益 SRC 按固定六项填：漏洞 URL、归属证明、首页截图（含地址栏）、漏洞证明、权重选择、活动/任务选择 | 按字段填：漏洞标题、基本信息（类型 / 等级 / 厂商信息）、漏洞简述、漏洞正文、修复建议 |
| 标题 | 简明扼要说明问题，语言规范 | 通常写成「XX 企业（或公司）存在 XX 漏洞」；只写漏洞类型会被忽略 |
| 厂商信息 | 输入漏洞 URL 后系统自动关联厂商 | 需**自己填**，填错或不填会被忽略处理 |
| 权重 / 活动 | 独有：按主域名权重选择，活动/任务需事先报名领取 | 无此字段 |
| 描述结构 | 一段「漏洞描述」写到底 | 分「漏洞简述」（概述 + 危害）与「漏洞正文」（复现过程 + 危害证明） |
| 复现证据 | 步骤 + 截图；支持上传复现视频（MP4） | 分步骤图文描述，**每个步骤都要有图文**；无利用截图或无详细过程会被忽略 |
| 修复建议 | 要具体、可落地 | 明确要求对开发有实用性——修复思路、修复代码样式或伪代码；无效建议会被忽略 |
| 审核侧重 | 偏业务影响与数据量 | 强调「一次性能复测完成」，步骤与证据要自洽 |
| 忽略理由 | 厂商侧可忽略：误归属、漏洞重复、无影响 | 类型/厂商信息写错、无利用截图、无详细过程、无效修复建议 |

两家的共同点：**格式排版要规范，无病句错别字，用语专业化**（漏洞盒子把这条写进了报告标准）。别小看它——错别字和混乱排版会让审核员先入为主地怀疑这份报告的质量。

各平台表单字段会调整，**最终以提交页面当前要求为准**。

### 7. 会直接判定为重复或忽略的规则

这一类最容易被忽略，因为报告本身写得没问题，是**判定口径**的问题：

**同一个源产生的漏洞算一个。** 漏洞盒子的评定原则列得很细：同一个接口引起的多个漏洞、框架导致的整站漏洞、同一上传组件在不同功能处产生的上传漏洞、同一文件的不同参数、相同功能处（增删改）的同类型漏洞、一处报错引发的多个页面信息泄露——**按同一漏洞合并处理**。所以不要把一个接口上的多个问题拆成多份报告。

**前后关联的合并。** 先提交「弱口令进后台」，再提交「进后台之后发现的 SQL 注入 / 越权」，后一份会被合并处理。

**弱口令同系统只认第一个。** 同一套系统的多个用户弱口令，只确认第一个；同一用户的弱口令能登录多个系统，算同一个漏洞。

**同一个漏洞只写一份报告**——这一条和上面两条方向相反，但同样要记住。补天把「将一个完整漏洞拆分为多个漏洞提交以谋取更多奖励」明确列为恶意刷洞，扣信誉值、情节严重者封号。

**不要拿别处的洞来充数。** 漏洞盒子把「将他平台已知的、公开的、已修复的漏洞未经验证重复提交」列为处罚条件。

**厂商未认领也能忽略。** 补天在厂商认领阶段，厂商可以以「误归属 / 漏洞重复 / 无影响」为由忽略漏洞——**三条里有两条是报告本身可以避免的**。

### 8. AI 辅助报告的红线

两家的公告要点合并成六条：

1. **人工验证是前提**。AI 可用于辅助挖掘、POC 编写、报告整理，但漏洞是否真实存在、是否可复现、是否有实际影响，必须由提交者人工判断和验证。
2. **报告内容要人工逐条核对**，确认漏洞真实存在且描述与实际一致后，才能提交。
3. **禁止批量提交**——包括用工具自动扫描、自动生成描述后直接上报。
4. **不得用通用模板代替真实测试过程**。报告要包含充分的技术细节和有效复现步骤。
5. **必须提供的证据**：漏洞 URL、漏洞所在功能点、漏洞验证过程、完整数据包及 POC、漏洞验证证明、危害证明，以及对应的细节截图与文字描述。
6. **以下情况按无效报告驳回**：描述明显由 AI 推测、复现步骤不可执行或与目标系统不匹配、未提供关键截图与请求包/响应包、内容存在幻觉（虚构接口、虚构参数、虚构影响）、批量提交高度相似的低质量报告。**累计超过 3 个会被提醒，超过 5 个扣信誉值 / 限制提交权限。提交者对所提交报告的真实性负完全责任，无论是否借助 AI。**

结论落在工作方式上：**AI 只承担「把已确认的事实组织成平台要的结构」这一段**。事实从哪来？从人工验证记录里来。报告里出现任何一个没验证过的接口名、参数名、影响描述，都是给整份报告埋雷——审核员复测对不上，退单事小，账号受限事大。

### 9. 提交之后：进度、忽略与返工

提交不是终点。了解流程有两个用处：知道什么时候该跟进，以及被打回时怎么改。

- **进度**：补天在厂商认领阶段通常要等 7 天左右，之后 1–2 个工作日内确认；漏洞盒子互联网漏洞一般 1–10 天等厂商认领。等待期不必反复催。
- **查忽略原因**：补天在个人空间【漏洞列表】里，审核不通过后面有「原因」，鼠标移上去可见；漏洞盒子的处理结果会在报告详情里给。**先看平台给的理由，再改报告**——很多返工失败是因为按自己的猜测改，没对着平台的理由改。
- **常见理由对应的动作**：说「无法复现」→ 补前置条件、补完整请求包与截图；说「危害不足」→ 补危害证明、把字段数出来、写清影响范围；说「重复」→ 查是这个系统的第几个同类问题，判断是否还有必要继续；说「证据不全」→ 按第 8 节第 5 条那六项逐项补齐。
- **一条硬规矩**：同一个漏洞反复提交多份报告去试运气，属于刷洞行为，不要做。

## 提交前自检清单

交出去之前逐条过一遍，任一条不满足就回去补：

- [ ] 标题只陈述事实，没有「疑似 / 可能 / 存在风险」这类词，也不是只写漏洞类型
- [ ] 影响资产给的是**文字 URL**，写全，能直接复制访问
- [ ] 资产归属写清楚，与所报厂商一致（补天填归属证明，漏洞盒子填厂商信息）
- [ ] 漏洞类型与等级按平台预置分类填写，等级在危害说明里有对应依据
- [ ] 漏洞描述四要素齐全：组件与版本、漏洞编号、触发条件、影响面
- [ ] 复现步骤从零讲起，不跳步，每步标注了对应截图，且**没有超出第 3 节的证明上限**
- [ ] 请求与响应是原始文本，未改写、未补全；POC 是文本不是截图
- [ ] 危害说明落到具体能力与范围，敏感信息数出了命中的字段
- [ ] 修复建议具体到版本号 / 配置项 / 代码行
- [ ] 报告里没有任何未验证过的内容（接口、参数、影响描述逐条核对）
- [ ] 确认这个漏洞不是同一个源的重复项，也没有和已提交的漏洞拆开报
- [ ] 待补截图清单已单独列出，交给人工补齐
- [ ] 格式排版干净，无病句错别字
- [ ] 测试范围全部在授权域名内，报告里没有出现范围外的资产
